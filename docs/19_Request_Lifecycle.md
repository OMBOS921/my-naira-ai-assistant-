# 19. Request Lifecycle & Event Flow

This document defines how a user request flows through the system and how asynchronous events propagate. It covers the synchronous Mediator path (request-response) and the asynchronous Event Bus path (pub-sub), including error handling and timeout policies.

---

## 1. Request Data Model

Every user interaction is wrapped in a standardised `UserRequest` object before entering the Orchestrator.

| Field | Type | Description |
|---|---|---|
| `id` | `uuid.UUID` | Unique request identifier (generated by the Presentation layer) |
| `source` | `Literal["cli", "websocket", "voice"]` | Origin of the request |
| `text` | `str` | The raw input text (transcribed if voice) |
| `session_id` | `str` | Active session token |
| `timestamp` | `float` | Unix timestamp of receipt |
| `metadata` | `dict[str, Any]` | Extensible bag for future fields (e.g., `language`, `client_version`) |

The `UserRequest` is an immutable dataclass. Once created, it must not be mutated by any layer.

---

## 2. Synchronous Request Flow (Mediator Pattern)

The flow is managed entirely by the Orchestrator. Modules never communicate directly; all data passes through the Orchestrator.

```
Phase 1          Phase 2         Phase 3         Phase 4           Phase 5           Phase 6           Phase 7          Phase 8
┌─────────┐     ┌──────────┐    ┌──────────┐   ┌───────────┐     ┌───────────┐     ┌───────────┐     ┌──────────┐    ┌──────────┐
│Capture &│     │ Security │    │ Context  │   │  Prompt   │     │    LLM    │     │   Tool    │     │ Response │    │ Delivery │
│ Enqueue │────▶│  Gate    │───▶│ Assembly │──▶│Compilation│────▶│ Inference │────▶│ Execution │────▶│Compilation│───▶│          │
└─────────┘     └──────────┘    └──────────┘   └───────────┘     └───────────┘     └───────────┘     └──────────┘    └──────────┘
                                                                       │                                      │
                                                                       │ (tool call detected in response)      │
                                                                       └──────────────────────────────────────┘
```

### Phase 1: Capture & Enqueue

- **Owner:** Presentation Layer (CLI reader task, WebSocket handler)
- **Action:**
  1. Read raw input string.
  2. Wrap in a `UserRequest` dataclass.
  3. Call `await orchestrator.process_request(request)`.
- **Constraint:** The Presentation layer holds no reference to business logic, AI modules, or service modules. It only holds a callable reference to the Orchestrator's `process_request` method, injected at boot time.
- **Timeout:** N/A (blocking on user input).

### Phase 2: Security Gate

- **Owner:** Orchestrator → Security Manager
- **Action:**
  1. Orchestrator transitions FSM to `PROCESSING`.
  2. Orchestrator calls `security_manager.validate_input(request.text)`.
  3. The Security Manager runs:
     - Regex-based prompt injection detection (Phase 1 implementation; enhanced in later phases).
     - Payload length check (reject if > `config.security.max_input_length`, default 32 768 characters).
     - Allowed-character filter (reject raw control characters except `\n`, `\t`).
  4. Returns `ValidationResult(status, sanitized_text, reason)`.
- **On rejection:** Orchestrator sends an error response to the Presentation layer: `"Request blocked by security policy: {reason}"`. FSM returns to `IDLE`.
- **On acceptance:** The `sanitized_text` replaces `request.text` for the remainder of the pipeline.
- **Timeout:** Max 2 s. If exceeded, fall back to accepting the input (fail-open would be unsafe; fail-closed with an error message is preferred).

### Phase 3: Context Assembly

- **Owner:** Orchestrator → Context Manager
- **Action:**
  1. Orchestrator calls `context_manager.build_context(request.session_id, request.text)`.
  2. Context Manager loads conversation history for `session_id` (via MemoryPort — see `20_Dependency_Rules.md` for the Port/Adapter pattern).
  3. Applies sliding window: truncates oldest entries until token count ≤ `config.context.max_tokens` (default 4096).
  4. Inserts the current user text as the latest message.
  5. Returns `Context(system_prompt, messages, token_count)`.
- **Timeout:** Max 5 s. If exceeded, return a minimal context with the current message only.

### Phase 4: Prompt Compilation

- **Owner:** Orchestrator → Prompt Manager
- **Action:**
  1. Orchestrator calls `prompt_manager.compile(context)`.
  2. Prompt Manager loads the system prompt template from `backend/modules/prompt/templates/`.
  3. Renders template variables (date, user name, active capabilities list, etc.) from the context and config.
  4. Returns the final prompt string.
- **Timeout:** Max 1 s. Pure string operations — timeout indicates a bug.

### Phase 5: LLM Inference

- **Owner:** Orchestrator → LLM Manager
- **Action:**
  1. Orchestrator calls `await llm_manager.generate(prompt, context.messages)`.
  2. LLM Manager selects the active provider (Gemini, Ollama, DeepSeek) based on `config.llm.active_provider`.
  3. Sends the request via the selected provider's adapter.
  4. Returns `LLMResponse(text, tool_calls, finish_reason, token_usage)`.
- **Tool calls:** If `tool_calls` is non-empty, the request enters Phase 6. Otherwise, skip to Phase 7.
- **Timeout:** Configurable per provider (default 30 s for API, 120 s for local Ollama). On timeout, retry once with a different provider if available; otherwise return an error response.
- **Provider fallback order:** `config.llm.fallback_chain` (e.g., Gemini → Ollama → DeepSeek).

### Phase 6: Tool Execution

- **Owner:** Orchestrator → Capability Manager → specific module
- **Action:**
  1. For each tool call in `LLMResponse.tool_calls`:
     a. Orchestrator calls `capability_manager.resolve(tool_name)`.
     b. Capability Manager looks up the registered module for that tool name.
     c. If the module is `lazy` and not yet loaded, the Orchestrator triggers lazy-loading (see `18_Boot_Sequence.md §3`).
     d. Orchestrator calls `await module.execute(tool_name, tool_args)`.
     e. The module executes the action and returns a `ToolResult(status, output, error)`.
  2. All tool results are collected into a `list[ToolResult]`.
  3. Orchestrator calls `llm_manager.generate(prompt, messages + tool_results)` for a second-pass LLM call that incorporates the tool outputs.
  4. The second-pass response is the final `LLMResponse`.
- **Constraint:** No module may call another module directly. Every module interaction goes through the Orchestrator.
- **Timeout:** Per-tool timeout is defined in `config.tools.{name}.timeout` (default 15 s). If a tool times out, the Orchestrator sends a `ToolResult(status="timeout", error="...")` to the LLM as if the tool returned an error.
- **Security:** Every tool execution passes through the Permission Gatekeeper (see `09_Security.md`). Dangerous actions prompt the user for approval before execution begins.

### Phase 7: Response Compilation

- **Owner:** Orchestrator
- **Action:**
  1. Extract the final `LLMResponse.text`.
  2. If voice mode is active and the response is marked as speakable, Orchestrator calls `await voice_module.speak(response.text)` (Phase 6 — but only if TTS is loaded).
  3. Package the response into `UserResponse(request_id, text, source, duration_ms)`.
- **Timeout:** TTS timeout is 60 s per utterance. If exceeded, fall back to printing the text.

### Phase 8: Delivery

- **Owner:** Orchestrator → Presentation Layer
- **Action:**
  1. Orchestrator calls `presentation.send_response(user_response)`.
  2. The Presentation layer prints (CLI) or sends (WebSocket) the response.
  3. Orchestrator transitions FSM: if TTS is speaking → `SPEAKING`, otherwise → `IDLE`.

## 3. Asynchronous Event Flow (Event Bus)

### Event Data Model

| Field | Type | Description |
|---|---|---|
| `type` | `str` | Dot-separated event type (e.g., `system.battery_low`) |
| `source` | `str` | Module name that published the event |
| `data` | `dict[str, Any]` | Payload |
| `priority` | `Literal["high", "normal", "low"]` | Dispatch priority |
| `timestamp` | `float` | Unix timestamp |

### Event Types

| Event Type | Source Layer | Description | Subscribers |
|---|---|---|---|
| `system.shutdown` | Orchestrator, OS Layer | Graceful shutdown request | Orchestrator (self) |
| `system.memory_warning` | Utils/Monitor | RAM usage exceeds threshold | Orchestrator, Session Manager |
| `system.error` | Any module | Unrecoverable module error | Orchestrator, Logger |
| `permission.granted` | Security Manager | User approved an action | Orchestrator, Session Manager |
| `permission.revoked` | Security Manager | Permission session expired | Orchestrator, Session Manager |
| `module.loaded` | Orchestrator | A lazy module finished loading | Capability Manager |
| `module.degraded` | Orchestrator | A module failed to load | Capability Manager, Logger |

### Subscription Model

1. Modules subscribe during registration in Step 7 of the boot sequence.
2. Subscription is explicit: `orchestrator.on(event_type, callback)`.
3. A module may only subscribe to events for which it has a legitimate need (enforced by review, not by code at this phase).
4. The Orchestrator is the default subscriber for all `system.*` events.

### Dispatch Guarantees

1. **Ordering:** Events of the same `type` are delivered in FIFO order. Cross-type ordering is not guaranteed.
2. **Delivery:** At-most-once delivery. If a subscriber's callback raises, the exception is logged and the event is dropped for that subscriber. Other subscribers still receive the event.
3. **Async:** All callbacks are async coroutines. The Event Bus dispatches via `asyncio.create_task()` to avoid blocking the publisher.
4. **Backpressure:** If the pending event queue exceeds `config.event_bus.max_queue_size` (default 1 000), new events of `priority: "low"` are dropped. `high` and `normal` priority events block the publisher until queue space is available.

### Event Flow Example: Low Battery

```
┌─────────┐   fire          ┌───────────┐   dispatch    ┌──────────────┐
│OS Monitor│ ──────────────▶ │ Event Bus │ ────────────▶ │ Orchestrator │
│(Layer 6) │ "system.       │(owned by  │  callback     │  (Layer 3)   │
│          │  battery_low"  │Orchestr.) │               │              │
└──────────┘                └───────────┘               └──────┬───────┘
                                                               │
                                              ┌────────────────┴────────┐
                                              ▼                         ▼
                                      ┌──────────────┐        ┌────────────────┐
                                      │  Presentation│        │   Context      │
                                      │  Layer (CLI) │        │  Manager       │
                                      │  "Warning:   │        │  (inject into  │
                                      │   Battery    │        │   next prompt) │
                                      │   low."      │        └────────────────┘
                                      └──────────────┘
```

## 4. Error Handling

### Module-Level Error

If a module raises during request processing:

1. The Orchestrator catches the exception.
2. Logs a structured error record: `[ERROR] [module_name] [request_id] [exception_type]: [message]`.
3. If the module implements `degrade()` (optional callback), the Orchestrator calls it to release heavyweight resources.
4. The Orchestrator falls back to a degraded response: `"I encountered an error while processing that request. The {module_name} module is temporarily unavailable."`
5. The module is marked `degraded` in the Capability Manager registry. Subsequent requests involving that module return the degraded response immediately without retrying.

### Provider-Level Error (LLM)

If an LLM provider returns a 5xx, rate-limit, or timeout:

1. LLM Manager logs the error.
2. If `config.llm.fallback_chain` lists an alternative provider, the LLM Manager retries the request with the next provider in the chain.
3. If all providers fail, the Orchestrator returns `"I'm unable to process that request right now due to an AI service outage."`
4. The last-used provider is NOT penalised; the next request will try the primary provider again.

## 5. Timeout Policy

| Phase | Stage | Default Timeout | Behaviour on Expiry |
|---|---|---|---|
| 2 | Security Gate | 2 s | Reject request with security error |
| 3 | Context Assembly | 5 s | Return minimal context (current message only) |
| 4 | Prompt Compilation | 1 s | Return error; treat as module degradation |
| 5 | LLM Inference | 30 s (API) / 120 s (local) | Retry with fallback provider; if none, return error |
| 6 | Tool Execution | 15 s per tool | Send `ToolResult(status="timeout")` to LLM |
| 6 | Tool Lazy-Load | 30 s per module | Mark module `degraded`; return error to user |
| 7 | TTS Speech | 60 s per utterance | Fall back to text output |

All timeouts are configurable per phase via `config/timeouts.yaml`.
