# 19. Request Lifecycle & Event Flow

This document defines how a user request flows through the system and how asynchronous events propagate. It covers the dual Presentation entrypoints (`run_cli.py` and `main.py` WebSocket), the deterministic Master Fast Command Router (FCR Phase 2), the synchronous Mediator path (request-response), the LLM tool-calling loop, and the asynchronous Event Bus pub-sub path.

---

## 1. Request Data Model

Every user interaction is wrapped in an immutable `UserRequest` object before entering the system.

| Field | Type | Description |
|---|---|---|
| `id` | `uuid.UUID` | Unique request identifier (generated by Presentation layer) |
| `source` | `Literal["cli", "websocket", "voice"]` | Origin of the request |
| `text` | `str` | The raw input text (transcribed if voice) |
| `session_id` | `str` | Active session token (e.g. `"cli_session"`, `"default"`) |
| `timestamp` | `float` | Unix timestamp of receipt |
| `metadata` | `dict[str, Any]` | Extensible payload bag (e.g. `client_version`, `user_name`) |

## 3. Detailed Request Lifecycle Phases

### Phase 1: Capture & Gateway Ingestion
- **Entrypoints:**
  - **CLI Terminal Loop (`run_cli.py`):** Captures user input via non-blocking `asyncio.to_thread(input, "You: ")`.
  - **WebSocket Server (`main.py`):** Receives JSON payloads on `/ws/naira`. Handles special control types:
    - `system_init`: Extracts `session_id` and `user_name`, explicitly triggering `SessionManager`, `ConversationManager`, and `InteractionManager` state synchronization before returning identity ACK.
    - `barge_in` / `interrupt`: Sets audio interrupt event to halt active speech playback immediately.
- **Output:** Construct immutable `UserRequest(id, source, text, session_id, timestamp)`.

### Phase 1.5: Fast Command Routing (FCR Phase 2)
- **Owner:** `FastCommandRouter`
- **Action:**
  1. Inspects `UserRequest.text` against deterministic phrase patterns.
  2. Computes dynamic length-weighted candidate scores for system intents (app launch, volume control, file operations, system shutdown/lock).
  3. **On Match (< 5ms):** Executes OS action directly via `PCControlManager` or system APIs, produces standard response, and bypasses LLM inference entirely.
  4. **On Miss:** Forwards request to Phase 2 (Security Gate).

### Phase 2: Security Gate
- **Owner:** Orchestrator → Security Manager
- **Action:**
  1. Transition FSM state to `PROCESSING`.
  2. Validate input length (< 32,768 chars) and sanitize control characters.
  3. Perform prompt injection pattern matching.
- **On Rejection:** Return `"Request blocked by security policy: {reason}"` and reset FSM to `IDLE`.

### Phase 3: Context Assembly & Session Sync
- **Owner:** Context Manager & Session Manager
- **Action:**
  1. Fetch active context history for `request.session_id`.
  2. Apply sliding window token truncation (budget ≤ 4,096 tokens).
  3. Inject active user message.

### Phase 4: Prompt Compilation
- **Owner:** Prompt Manager
- **Action:** Render template variables (user name, system capabilities, date/time, personality directives) into the final system prompt.

### Phase 5: LLM Inference & Caching Rules
- **Owner:** LLM Manager & `LLMResponseCache`
- **Action:**
  1. Query `LLMResponseCache` using SHA-256 key (prompt + context + tools).
  2. **Cache Hit:** If cached response exists and is unexpired, return immediately (< 2ms).
  3. **Cache Miss:** Invoke `LLMProviderOrchestrator` across fallback chain (`gemini` → `ollama` → `deepseek`).
  4. **Caching Rule:** Store response in LRU cache **only if `response.tool_calls` is None or empty**. Responses containing tool calls are NEVER cached to ensure destructive tool actions are never blindly replayed.

### Phase 6: Tool Resolution & Skill Pack Execution
- **Owner:** Tool Router & `CodingAgentManager` / Capability Modules
- **Action:**
  1. If `LLMResponse.tool_calls` is present:
     a. Route tool calls to registered tool handlers or `CodingAgentManager` Skill Packs (24 domain packs).
     b. Track execution state via `ActionLifecycle` (`ACKNOWLEDGED`, `IN_PROGRESS`, `COMPLETED`, `FAILED`).
     c. Pass tool execution outputs back into LLM for second-pass synthesis.
  2. `InteractionManager` observes action lifecycle events and generates natural conversational updates adapted to the active personality profile (`professional`, `friendly`, `close_friend`, `minimal`).

### Phase 7: Response Delivery & Speech
- **Owner:** Presentation Gateway & Voice Service
- **Action:**
  1. Package `UserResponse(request_id, text, source, duration_ms)`.
  2. Deliver text to CLI stdout or WebSocket JSON payload.
  3. If voice output is enabled and `SilencePolicy` permits, synthesize audio via `VoiceManager` (`pyttsx3`).
  4. FSM transitions to `IDLE`.

## 4. Asynchronous Event Flow (Event Bus)

### Priority Event Dispatch
The system runs a thread-safe `EventBus` supporting dot-separated topic subscriptions (`system.battery_low`, `interaction.progress`, `watchdog.alert`).

| Priority | Handling Policy |
|---|---|
| `HIGH` | Dispatched immediately; blocks publisher if event queue is full. |
| `NORMAL` | Standard FIFO queue dispatch. |
| `LOW` | Automatically dropped under heavy backpressure (queue size > 1,000). |

### Watchdog Alert Cycle Example
```
┌───────────────────┐    High Load    ┌───────────┐   Publish   ┌────────────────────┐
│ ProactiveWatchdog │ ──────────────▶ │ Event Bus │ ──────────▶ │ InteractionManager │
│ (CPU/RAM Sampled) │                 └───────────┘             └─────────┬──────────┘
└───────────────────┘                                                     │
                                                                          ▼
                                                                [ Broadcast Voice / UI ]
```
